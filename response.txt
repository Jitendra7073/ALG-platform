PRODUCTION FIX PLAN
Overview
This plan addresses critical issues in priority order while maintaining backward compatibility. Each phase is independently deployable.

PHASE 1: Authentication & Authorization (Week 1)
Why First?
Open APIs are the highest security risk. Without auth, all other fixes are meaningless.

Design: Simple API Token System
Components:

API Token middleware - Bearer token validation
Environment-based config - API_TOKEN in .env
Route protection levels - Public vs Protected vs Admin
Implementation:


1. Create src/middleware/auth.js
   - validateBearerToken(req, res, next)
   - validateAdminToken(req, res, next) // For destructive operations

2. Generate secure token for .env:
   - node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

3. Apply protection levels:
   
   PUBLIC (no auth):
   - GET /api/logs/* (monitoring)
   - GET / (frontend)
   
   PROTECTED (bearer token):
   - All GET endpoints (data reads)
   - POST/PUT non-destructive operations
   
   ADMIN (bearer + admin check):
   - DELETE /api/delete-all
   - DELETE /api/sites/bulk
   - POST /api/scraper/start/*
   - POST /api/email/campaigns/*/start

4. Add optional frontend auth:
   - Store token in localStorage
   - Add Authorization header to all fetch() calls
   - Redirect to login if 401 received
Risks if skipped:

Anyone can delete all data
Competitors can scrape your leads
Email credentials exposed
Backward compatibility:

Optional mode: if API_TOKEN not set, allow all requests (dev mode)
Add AUTH_REQUIRED=true env var to enable enforcement
PHASE 2: Async Correctness (Week 1-2)
Why Second?
Broken async calls return Promise objects instead of data, causing silent failures.

Systematic Fix Strategy
The Problem Pattern:


// WRONG - returns Promise object
app.get("/api/stats", (req, res) => {
  const stats = db.getStatistics(); // Missing await
  res.json({ success: true, data: stats });
});
Fix Strategy - File by File:

File	Functions to Fix	Approach
server.js	All route handlers	Add async to handler, await to DB calls
database.js	All exported functions	Already async - verify callers use await
email-senders-templates-api.js	All router handlers	Add async to handlers
timezone-aware-api.js	All router handlers	Add async to handlers
linkedin-credentials-api.js	All router handlers	Add async to handlers
Execution Steps:


1. Global search for "db\." in route handlers
2. For each match, verify:
   - Handler function has 'async' keyword
   - db.all(), db.get(), db.run() have 'await' keyword
   
3. Fix pattern:
   Before: app.get("/path", (req, res) => { const x = db.get(...); ... })
   After:  app.get("/path", async (req, res) => { const x = await db.get(...); ... })

4. Test endpoints that return Promise objects:
   - /api/stats
   - /api/keywords
   - /api/contacts/stats
   - /api/executives/stats
   - /api/excluded-domains
   - /api/ignored-tags
   - /api/searches
Validation Script:


// Add to tests - endpoint should return object, not Promise
fetch('/api/stats').then(r => r.json()).then(d => {
  console.assert(typeof d.data === 'object', 'Stats should be object');
  console.assert(d.data.constructor !== Promise, 'Should not be Promise');
});
Risks if skipped:

APIs return { success: true, data: [object Promise] }
Frontend receives unusable data
Silent data corruption
PHASE 3: Job Safety & Race Conditions (Week 2)
Why Third?
Scrapers running concurrently can corrupt data and waste resources.

Design: Simple In-Memory Lock
Components:

Lock map - Track active operations
Lock acquisition - Check-and-set pattern
Lock release - Guaranteed cleanup (finally block)
Fix Areas:

Area	Issue	Fix
Scraper start	Multiple requests can start same keyword	Add to runningScrapers before any async work
Email worker	Parallel sends can exceed daily limits	Track activeSendsPerSender (already exists, verify it works)
AI processor	Same site processed by multiple workers	Add processing flag with timeout
Implementation:


SCRAPER START FIX:
1. Add to runningScrapers IMMEDIATELY (before any async):
   const keywordId = parseInt(req.params.keywordId);
   if (runningScrapers.has(keywordId)) {
     return res.status(400).json({ error: "Already running" });
   }
   runningScrapers.set(keywordId, { status: "starting", ... });

2. Wrap entire runScraper in try/finally:
   try {
     await runScraper(...);
   } finally {
     runningScrapers.delete(keywordId);
   }

3. Add timeout protection:
   const scraper = runningScrapers.get(keywordId);
   if (scraper && Date.now() - scraper.started > MAX_SCRAPER_TIME) {
     runningScrapers.delete(keywordId); // Force cleanup
   }

EMAIL WORKER FIX:
1. Verify activeSendsPerSender is atomic:
   async sendEmail(senderId, email) {
     const current = this.activeSendsPerSender.get(senderId) || 0;
     if (current >= this.maxParallelPerSender) return false;
     this.activeSendsPerSender.set(senderId, current + 1);
     try {
       await this.sendNow(email);
     } finally {
       this.activeSendsPerSender.set(senderId, current);
     }
   }

2. Add sender.sent_today check INSIDE transaction:
   await db.transaction(async (tx) => {
     const sender = await tx.get("SELECT sent_today FROM email_senders WHERE id = $1", [senderId]);
     if (sender.sent_today >= sender.daily_limit) throw new Error('Limit reached');
     await tx.run("UPDATE email_senders SET sent_today = sent_today + 1 WHERE id = $1", [senderId]);
     await sendEmail(email);
   });
Risks if skipped:

Daily limits exceeded
Multiple scrapers hitting same sites
Resources wasted on duplicate work
PHASE 4: Standard API Response Contract (Week 3)
Why Fourth?
Inconsistent responses cause frontend bugs but don't crash the system.

Design: Unified Response Wrapper
Standard Format:


{
  success: boolean,
  data?: any,           // Successful GET requests
  message?: string,     // Successful POST/PUT/DELETE
  error?: string,       // Error messages
  code?: string,        // Machine-readable error code
  meta?: {              // Pagination, totals
    page?: number,
    limit?: number,
    total?: number,
    hasMore?: boolean
  }
}
Implementation Strategy:


1. Create response helper:
   // src/utils/response.js
   function success(res, data, meta) {
     return res.json({ success: true, data, ...(meta && { meta }) });
   }
   function successMessage(res, message) {
     return res.json({ success: true, message });
   }
   function error(res, statusCode, code, message) {
     return res.status(statusCode).json({ success: false, code, error: message });
   }

2. Define error codes:
   const Errors = {
     NOT_FOUND: 'NOT_FOUND',
     VALIDATION: 'VALIDATION_ERROR',
     DUPLICATE: 'DUPLICATE',
     UNAUTHORIZED: 'UNAUTHORIZED',
     FORBIDDEN: 'FORBIDDEN',
     CONFLICT: 'CONFLICT', // For race conditions
     INTERNAL: 'INTERNAL_ERROR'
   };

3. Migration path (no breaking changes):
   - Week 1: Add helpers, use in NEW endpoints only
   - Week 2: Update GET endpoints (data returns)
   - Week 3: Update POST/PUT/DELETE endpoints
   - Week 4: Update error handling

4. Frontend can handle both formats during transition:
   function isSuccess(response) {
     return response.success === true || response.data !== undefined;
   }
Risks if skipped:

Frontend must handle multiple response formats
Harder to debug API issues
No standardized error codes for client handling
PHASE 5: Input Validation (Week 3-4)
Why Last?
Validation prevents bad data but doesn't cause system failures.

Design: Middleware-Based Validation
Components:

Validation middleware - Using express-validator
Schema definitions - Per-endpoint rules
Sanitization - Trim, escape, type coerce
Priority Endpoints:

Priority	Endpoints	Why
1	All DELETE endpoints	Prevent accidental mass deletion
2	POST /api/campaigns	Prevent invalid email sends
3	POST /api/senders	Prevent invalid SMTP config
4	POST /api/keywords	Prevent scraper abuse
Implementation:


1. Install: npm install express-validator

2. Create validation schemas:
   // src/validators/schemas.js
   const keywordSchema = [
     body('keyword').trim().isLength({ min: 1, max: 100 }).notEmpty(),
     body('max_sites').optional().isInt({ min: 0, max: 10000 })
   ];

3. Validation middleware:
   const { validationResult } = require('express-validator');
   const handleValidation = (req, res, next) => {
     const errors = validationResult(req);
     if (!errors.isEmpty()) {
       return res.status(400).json({
         success: false,
         code: 'VALIDATION_ERROR',
         error: errors.array().map(e => `${e.path}: ${e.msg}`).join(', ')
       });
     }
     next();
   };

4. Apply to routes:
   app.post("/api/keywords", keywordSchema, handleValidation, async (req, res) => {
     // Handler - now safe from invalid input
   });
Risks if skipped:

Invalid data enters database
Scraper crashes on malformed input
Email sends to invalid addresses
